The problem with AI-built software

How decision-lock fixes it

The problem
The fix
01 Decisions get dropped. AI silently skips or reinterprets what you decided.
01 One decision log is the single source of truth. One test per decision, named after it, run on a real throwaway database.
02 False "done". It says "tests pass" when they don't.
02 An independent agent (not the builder; a different vendor is recommended) reproduces the run. "Done" means reproduced, not claimed.
03 Self-graded tests. The AI that wrote the code writes the tests, so they check what it built, not what you decided.
03 A separate certifier session re-runs everything on a fresh database and attacks it with its own broken copies.
04 Tests that pass on anything. Weak or vacuous assertions prove nothing.
04 Mutation testing. Deliberately broken copies must be caught by a named failing assertion, or the test has no teeth.
05 Context loss. Across sessions and agents, earlier decisions are forgotten.
05 Small slices of 10, run in parallel. Each slice is checked against the log, never against memory.
06 No audit trail from a decision to proof that it holds.
06 Automatic fix loops. Failures go back to the builder on their own. A human hears about it only after 3 loops, with the root cause already found.

How it installs

Install once, generate a lock for each project

STEP 01Five questionsIn your project it asks: where are the decisions, how does a throwaway copy run, what asserts each one, what proof is kept, can slices run side by side.
STEP 02You approve the toolsIt lists every tool and why this project needs it, then waits for your go. Nothing is written before that.
STEP 03It writes your lock skillA project-specific lock skill at .agents/skills/ with one command that launches, checks, runs, collects evidence and cleans up.
STEP 04It breaks it on purposeOne decision is broken, the check must fail by name, the file is restored byte for byte, the check must pass again.
STEP 05It proposes one ruleOne line for the project's AGENTS.md (any agent can read it): show the evidence before calling a change done. Never applied without you.
STEP 06Teach it by exampleGive one good and one bad example. It writes the test and the mutant that proves the test can fail.
One command, one proof

A check you have never seen fail proves nothing

lock.sh: the single command
# every subcommand prints one JSON object
lock.sh launch            # start the throwaway copy
lock.sh doctor            # check the setup
lock.sh run <slice|ids>   # tests + mutants
lock.sh evidence          # collect the proof
lock.sh selftest D003    # break it, restore it
lock.sh cleanup           # remove the copy

Agent-agnostic

Roles, not vendors

Each role is just a command in one file, so any agent CLI, editor agent or human can fill it. The independent role must not be the same as the builder.

decision-lock.agents
# a role is not a vendor
BUILDER=writes the code and the report
CERTIFIER=judges the builder's work
INDEPENDENT=run-only, edits nothing
FIXER=applies fix briefs
# pipeline stops if INDEPENDENT == BUILDER
AGENTS.md: the one-line rule
Before you call any change that touches a
recorded decision done, run the
lock-<project> skill for those decisions
and show its evidence.
# proposed, never applied without you
TraceabilityLike regulated industries such as aerospace and medical: every decision links to a test, a mutant, and a report.
Confidence to let AI buildHand it real work. "Done" is proven by a run you did not have to trust.
